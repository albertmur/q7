## Cliente modelo servidor
- Todo el modelo está en la capa de aplicación. La interfaz es donde está el usuario, pero NO tiene nada que ver.
Tengo dos partes diferenciadas de una aplicación. El cliente conecta con el usuario.
La interfaz permite al usuario interactuar con la aplicación.
Todo esto está en el nivel de aplicación. 
Importante: como las aplicaciones estan separadas. Servidor donde hay información y un cliente que se conecta para poder "hacer cosas" con esa información.
Lo que el usuario le pide a la aplicación lo transforma en una llamada remota: cuando usamos el navegador, el servidor está fuera, el cliente responde a toda esa complejidad.

El servidor resuelve las peticiones de los clientes. Las recibe y responde. 
### Ejemplo
- Racó 
- Aplicación cliente servidor
- El cliente es el navegador. El navegador entiendo paginas HTML, hojas de estilo (CSS) y Javascript. Pero aquí no llega código Java. 
- En medio tenemos al protocolo HTTP, que tiene un formato de mensaje con unos comandos estandarizados.
- El servidor es HTTP y puede mostrar páginas dinámicas y estáticas.
- Mirar diapos de client application i Server application
- La idea es que el usuario puede enviar y recibir información. Para enviarla, usa formularios.

## Remote Invocation
El objetivo de la invocación remota es poder llamar a un servicio que está en otra máquina.
Tres modelos:
- RPC (Remote Procedure Call)
	- Primera forma de invocación remota
	- Llama remotamente a un procedimiento: 1 parámetro, 1 resultado
	- Se implementaban en lenguaje C y pensados para sistemas UNIX / Linux
	- Para poder generar estas interficies necesitabas XDR (el ejemplo de las transparencias es de reservas de vuela)
	- Reservasc para el cliente y reservass para el servidor
	- El último fichero común era el que tenía todos los tipos de datos, con las cabeceras
- RMI (Remote Method Invocation)
	- El mismo que RPC pero para objetos
	- Lo que comunico no es un procedimiento sino métodos de objeto
	- Llamas a un objeto remoto que está en otra máquina virtual
	- Como son máquinas virtuales de Java diferentes para el objeto es como si fueran objetos remotos
	- Como referencio a los objetos? Depende de lo que esté intentadno utilizar:
		- Un tipo básico, por valor
	- A la hora de implementar objetos, dos maneras:
		- Interfaz remota
			- Parte de aplicación cliente y parte de aplicación servidor
			- Lo que hace mi objeto en el cliente es a través de una referencia llamar al servidor
		- Interfaz serializable
			- Envía una copia bit a bit d leobjeto al cliente
			- Cogo el objeto en el servidor, lo serializo y aparece en la máquina del cliente 
	- Problemas de este modelo
		- Referenciar objetos remotos
		- Crear objetos remotos
		- La gestión de excepciones es complicada en cualquier aplicaicón distribuída (por eso en la práctica 2 hay muchos Try-Catch)
- CORBA
	- También orientado a objetos, pero se quiere comunicar objetos escritos en cualquier lenguaje sobre cualquier sistema operativo (e.g. conectar un cliente de c++ a un servidor de java)
	- Las comunicaciones son en binario
	- En la arquitectura tienes un cliente, un servidor, y un montón de servicios intermedios para que funcione. Muy complicado, no hace falta aprofundir.

## HTTP
- Tres versiones
- RFC --> Estándar del IETF
- Características
	- Protocolo sin estado
	- Protocolo petición - respuesta: por eso existen dos tipos de objetos: el request y el response. 
		- Para controlador el estado podemos usar cookies o sesiones. 
	- La mayoría de HTTP es HTTP3 que funciona con TCP
	- El puerto por defecto en la actualidad es el 443. En el lab usamos el 8080 porque todos los puertos por debajo del 1024 pertenecen al sistema y se necesitan permisos elevados para asignarlos.
### Funcionamiento
- Se abre una conexión de transporte / establezco comunicación (un extremo o el otro)
- Petición con comando
- Servidor la procesa y manda la respuesta
- Finalmente se cierra la conexión. La conexión no se cierra immediatamente para evitar tener que estar constantemente el 3WH
### Evolución
- Siempre tenemos dos partes separadas: cabeceras e información
- Problemas versión 3: como usa UDP, no se sabe si vamos a perder paquetes (hasta que un paquete no llega no puedes seguir procesando el siguiente, por lo que con UDP la aplicación se bloquea). Por este motivo aparece QUIC, un nivel por encima de UDP que controla que las cosas lleguen a tiempo. Mantengo UDP pero me aseguro que va a llegar todo en orden.
### Mensajes
- HTTP tiene unos mensajes con el formato de la transpa 45
	- Linea de petición: comando
	- Linea de respuesta: si la petición ha ido bien o mal
	- Parte de cabeceras:
		- Cabecera general: que día es hoy, si puedo hacer cache de la petición...
		- Cabecera específica de si es una petición o resppuesta:
			- Petición: que idioma entiendes, que tipo de navegados estás usando
			- Respuesta: qué tipo de servidor es, si es un apache, un nginx
		- Cabecera entidad:
			- Lo que está debajo:
				- Una página HTML con subtítulo, cualquier cosa
#### Message Request
- Ejemplo concreto de una cabecera HTTP
	1. Métodos HTTP. Los que más vamos a usar son GET (para hacer consultar) y POST (para casi cualquier cosa: consultar y enviar información). También hay otros métodos como PATCH, PUT, DELETE, HEAD. Lo primero que le diremos al servidor; el método que vamos a usar. SP significa espacio en blanco (todos los campos separados por SP). Resource_URL es la página a la que me quiero conectar. Otro espacio en blanco, después la versión de HTTP. Y finalmente un salto de línea con los carácteres CRLF (Carriage Return Line Feed)
	2. Request header
		1. Accept -> lo que acepta el navegador 
		2. Host -> el servidor al que se conecta
		3. User-agent -> la versión del navegador
#### Message reply
1. Código de stado: cómo ha ido la petición.
2. SP
3. Descripción del código de estado (e.g. 20X: OK)
	1. 20X -> La petición ha ido bien
	2. 30X -> Redirección a otra página
	3. 40X -> Error cliente
	4. 50X -> Error servidor
4. CRLF
5. Server program (?) y location para redirecciones
#### Métodos
- NOTA: En las prácticas siempre tendríamos que usar POST
- GET -> Método para hacer peticiones
	- Si en en login el formulario se envía con el método GET entonces en el enlace se verán los parámetros. Por lo que el usuario y el password apareceran en el enlace
	- Característica diferencial: puede pasar parámetros, pero NO modifica recursos.
- HEAD -> Lo mismo que GET pero me devuelve solo las cabeceras
- TRACE -> Para ver si todo va bien: mandas una petición y te la devuelve como se ha enviado
- OPTIONS -> Para pedirle las características al servidor. El servidor te devuelve todos los métodos que conozco. 
- DE MODIFICACIÓN:
	- Post: Lo puedo usar desde el formulario. Si en un formulario lo usamos, se pasan los datos por el cuerpo del mensaje en formato clave=valor. Pero si capturamos la red lo vamos a poder ver. Como mínimo ahora ya no se ve en la URL.
	- Put para crear recuross
	- Patch para actualizar el recurso
	- DELETE borra el recurso en concreto
